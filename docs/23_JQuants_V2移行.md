# 23. J-Quants API が V2 へ移行していた（HTTP 403 の原因）

## 23.1 何が起きたか

セットアップ画面で認証が `HTTP 403` で失敗した。

```
エラー: JQuantsError: auth_refresh が失敗しました: HTTP 403。
```

調べた結果、**原因はトークンの期限切れではなく、認証方式そのものの廃止**だった。

| | V1（旧） | V2（現行） |
|---|---|---|
| 認証 | メール/パスワード → リフレッシュトークン（1週間） → IDトークン（24時間） | **ダッシュボードで発行したAPIキーを `x-api-key` ヘッダに載せる** |
| ベースURL | `https://api.jquants.com/v1` | `https://api.jquants.com/v2` |
| 株価 | `/prices/daily_quotes` | `/equities/bars/daily` |
| 銘柄一覧 | `/listed/info` | `/equities/master` |
| TOPIX | `/indices/topix` | `/indices/bars/daily/topix` |
| 決算予定 | `/fins/announcement` | `/fins/earnings-date` |
| 列名 | `Open` / `AdjustmentClose` など | **`O` / `AdjC` など短縮形** |
| レスポンス | `{"daily_quotes": [...]}` | `{"data": [...], "pagination_key": "..."}` |

**V1 は 2026年6月1日に終了。** 2025年12月22日以降の登録者は V2 のみ。
利用者が「APIキーは発行済み」と言っていたのは **V2 のAPIキー**であり、
それを V1 の廃止済みエンドポイントに投げていたため 403 になった。

## 23.2 どう直したか

**エンドポイントやフィールド名を自分で推測するのをやめ、JPX 公式の Python クライアントを土台にした。**

- `jquants-api-client`（`jquantsapi.ClientV2`）を依存に追加
- `src/short_trade/jquants.py` は公式クライアントの薄いラッパに縮小。
  役割は「内部形式への正規化」と「ローカルキャッシュ」だけ
- 認証情報は `JQUANTS_API_KEY` の1つに統一。旧 `JQUANTS_REFRESH_TOKEN` /
  `JQUANTS_MAIL_ADDRESS` / `JQUANTS_PASSWORD` は `.env` から削除される
- セットアップ画面の入力欄をAPIキー1つに変更

### 列名の対応（v2 → 内部形式）

| v2 | 内部 | 備考 |
|---|---|---|
| `AdjO` / `AdjH` / `AdjL` / `AdjC` / `AdjVo` | `open` / `high` / `low` / `close` / `volume` | **調整済みを優先**（FR-105） |
| `O` / `H` / `L` / `C` / `Vo` | 同上 | 調整済みが無い場合のフォールバック |
| `Date` | index | — |

指数は `C` を `close` に、決算予定日は `SchDate`（予定日）を使う。
銘柄コードは v2 が5桁（末尾0）で返すことがあるため、内部では4桁に正規化する。

## 23.3 この失敗から入れた歯止め

| 対策 | 内容 |
|---|---|
| **公式クライアントに委ねる** | エンドポイント・パラメータ名・ページングを自前で持たない。仕様変更の追随は上流に任せる |
| **スキーマを推測せず突き合わせる** | `tests/test_setup_ui.py::test_to_bars_matches_official_v2_schema` が、使っている列名が `jquantsapi.constants.EQ_BARS_DAILY_COLUMNS_V2` に実在するかを毎回検査する |
| **列が変わったら実際の列名を出して落ちる** | `to_bars` は「想定した列がありません: [...]。実際の列: [...]」と表示する。次に仕様が変わったとき、原因の特定が数秒で済む |
| **フォールバック** | 調整済み列が無ければ素の列を使う |

## 23.4 記録として残す教訓

`docs/20` §20.4 に「J-Quants クライアントは実APIに対して未検証であり、
レスポンス形式は公開情報からの推定である」と書いていた。**その推定が実際に外れた。**

外れ方は「列名が少し違う」ではなく「**認証方式ごと廃止されていた**」という、
想定より一段深いものだった。**公開情報からの推定は、推定した本人が思うより外れる。**

`docs/19`（データ源の調査）で挙げた未確認事項 U-1〜U-6 も、同じ性質のリスクを抱えている。
接続が通った時点で実測に置き換える。

## 23.6 続き: 契約範囲外の日付で HTTP 400（U-1 の解決）

V2 へ移行後、次は別のエラーが出た。

```
400 body: Your subscription covers the following dates: 2016-09-10 ~ .
```

**これは失敗ではなく、U-1（遡れる期間）の答えだった。** 契約は **約10年分（2016-09-10〜）** を覆っている。

| 論点 | 結論 |
|---|---|
| U-1 遡れる期間 | **約10年（2016-09-10〜）** |
| VR-015（最低5年、できれば10年） | **満たしている** |
| §19.4 の一括取得案（有料プラン1か月契約→解約） | **不要になった** |
| U-2（解約後のデータ保持可否） | 一括取得しないため**論点が消滅** |

### 直し方

遡れる期間はプランごとに違い、事前に知る方法がない。**決め打ちをやめ、API のエラーメッセージから自動で読み取る**ようにした。

- `JQuantsClient.coverage()` … わざと 1990-01-01 を要求し、返ってきた範囲を読み取って以後キャッシュする
- `daily_quotes(..., clamp=True)` … 範囲外を要求したら、範囲内へ丸めて一度だけ取り直す
- `fetch --start` を省略すると契約範囲の最古日から取得する

**契約範囲に関係のないエラー（500 など）を握りつぶさない**ことをテストで固定した。
`clamp` はメッセージが読めたときだけ働き、読めなければそのまま送出する。
