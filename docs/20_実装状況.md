### 検証基盤の設計で守ったこと

| 要求 | 実装 |
|---|---|
| VR-001 二重実装の禁止 | 条件式は `catalog/rules/*.yaml` にしかない。コードは式を解釈するだけ |
| VR-002 ルックアヘッド防止 | 約定価格は必ず**翌営業日の始値**。判定日の終値では約定しない |
| DEC-004 / RM-001 損切り必須 | 損切り価格が決まらない候補はエントリーしない。仕様の時点でも弾く |
| RM-001a 論理ストップ | 終値がストップを割ったら**翌執行枠で成行**。逆指値は使わない |
| RM-001b 想定損失2倍 | サイズ計算は `(建値 − 損切り) × 2` を想定損失として扱う |
| FR-C07 選抜外の戦略は稼働不可 | `selfcheck` が `status: selected_*` を確認する |
| VR-011 スリッページ | 片道 0.10% を既定（成行のため保守的に） |
| PL-002 コスト | 手数料 0%（ゼロ革命）。料率は設定で変更可能 |

## 20.2 テストが見つけた仕様のバグ 2件

**基盤を作った最初の価値は、成績ではなくバグの検出だった。**

| # | バグ | 内容 | 修正 |
|---|---|---|---|
| 1 | `common.yaml` のレジーム条件が銘柄の終値を見ていた | `condition: "close > SMA(close, 200)"` と書いていたが、`close` は評価時に**当該銘柄の終値**に束縛される。TOPIX を見ているつもりで、実際は個別銘柄の200日線を見ていた | `INDEX.close > SMA(INDEX.close, 200)` に修正。`schema.md` に「指数を参照するときは必ず `INDEX.` を付ける」と明記 |
| 2 | `ST-04` が未定義の `return_126d` を参照していた | 相対強度の条件 `PCTRANK(return_126d, universe) >= 70` を書きながら、`return_126d` の定義がなかった | `definitions` に `close / close[-126] - 1` を追加 |

バグ1は**全戦略に影響する重大なもの**だった。書き下しただけでは気づかず、実行して初めて分かった。

## 20.4 J-Quants クライアントは未疎通

開発環境から `api.jquants.com` への通信がネットワークポリシーで遮断されていたため、
**実際の API に対しては一度も実行できていない。**

- 認証（リフレッシュトークン方式・メール/パスワード方式）、ページング、レートリミット、
  401時のトークン再取得、`AdjustmentClose` を優先する正規化までは実装済み。
- ただし**レスポンス形式は公開情報から推定したもの**であり、初回実行時に必ず目視で確認すること。
- 列名が違えば `to_bars()` が「想定した列がありません」と実際の列名を出して落ちる。

### 認証情報の渡し方

```bash
export JQUANTS_REFRESH_TOKEN="..."        # 推奨。漏洩時の影響が小さい
# または
export JQUANTS_MAIL_ADDRESS="..."
export JQUANTS_PASSWORD="..."
```

**リポジトリには絶対に置かない**（NFR-020 / `.gitignore` で `config/secrets.yaml` と `.env` を除外済み）。

## 20.6 使い方

```bash
pip install -r requirements.txt

# 仕様ファイルの検査（ネットワーク不要）
PYTHONPATH=src python -m short_trade selfcheck

# 合成データで基盤の健全性を確認（ネットワーク不要）
PYTHONPATH=src python -m short_trade smoke --strategy ST-06

# テスト
python -m pytest tests/ -q

# データ取得（要 J-Quants 認証情報）
PYTHONPATH=src python -m short_trade fetch --codes 7203,6758 --start 2015-01-01

# バックテスト
PYTHONPATH=src python -m short_trade backtest --strategy ST-06
```
