# 09. 非機能要求（NFR）・データ要求（DR）・システム構成方針

## 9.1 性能

> **改訂（2026-09-10）**: 半自動・日足スイング運用となったため、NFR-001〜005 は Phase 4 までは非適用。
> 代わりに「通知スケジュールの各時刻に処理が確実に走ること」と「スマートフォンでの画面表示速度」が要件となる（`docs/15`）。


| ID | 要求 | 目標値 | 優先度 |
|---|---|---|---|
| NFR-001 | ティック受信からシグナル判定完了までのレイテンシ | p95 ≤ 200ms、p99 ≤ 500ms | Must |
| NFR-002 | シグナル確定から発注APIコールまでのレイテンシ | p95 ≤ 100ms | Must |
| NFR-003 | 価格更新から損益画面反映まで（PL-020 と同一） | p95 ≤ 1s | Must |
| NFR-004 | 同時購読銘柄数 | 500 銘柄以上（Phase 3 時点） | Must |
| NFR-005 | ピーク時ティック処理スループット | 10,000 msg/s を欠落なく処理 | Should |
| NFR-006 | バックテスト速度 | 1銘柄・1年・分足を 10 秒以内 | Should |
| NFR-008 | スマートフォンでの初回表示（LCP） | 3G相当回線で 2.5 秒以内 | Must |
| NFR-009 | 通知の送信遅延（スケジュール時刻からの乖離） | 60 秒以内 | Must |
| NFR-007 | 遅延・キュー滞留が閾値を超えた場合、シグナル生成をスキップし記録すること（遅延データでの発注禁止） | — | Must |

## 9.2 可用性・信頼性

| ID | 要求 | 優先度 |
|---|---|---|
| NFR-010 | 立会時間中（9:00-15:30 JST）の稼働率 99.9% 以上 | Must |
| NFR-011 | 障害からの復旧目標時間（RTO）5分以内、データ損失許容（RPO）0（約定・注文・損益データ） | Must |
| NFR-012 | 発注・約定・損益に関わるデータは永続化され、プロセス再起動で失われないこと | Must |
| NFR-013 | 障害時は自動売買を安全側に停止し、人へ通知すること（RM-034 と一致） | Must |
| NFR-014 | 立会時間外にデプロイ・メンテナンスを行う運用とし、稼働中の無停止デプロイは必須としない | Should |
| NFR-015 | データベース・設定・監査ログの定期バックアップと、復旧手順の検証を行うこと | Must |

|---|---|---|
| NFR-020 | 証券会社の認証情報・APIキーを平文で保存しないこと（シークレット管理／暗号化必須） | Must |
| NFR-021 | 認証情報をログ・エラーメッセージ・画面に出力しないこと | Must |
| NFR-022 | 管理UIへのアクセスは認証必須とし、多要素認証を利用できること | Must |
| NFR-023 | 通信はすべて TLS で保護すること | Must |
| NFR-024 | 発注権限を持つコンポーネントを最小化し、権限分離すること | Should |
| NFR-025 | 依存パッケージの脆弱性を定期スキャンすること | Should |
| NFR-026 | 監査ログは追記専用とし、改ざん検知が可能であること | Should |

## 9.7 システム構成方針（参考。要件定義フェーズで確定）

- **構成要素**: Market Data Gateway / Feature Engine / Strategy Runner / Regime Detector /
  Decision Engine / Risk Gate / Order Router / Position & P&L Service / Reconciliation /
  Backtest Engine / Web UI / Notification / Audit Log Store。
- **配置**: 単一ホスト（プロセス分離）を初期構成とし、レイテンシ要件が満たせない場合のみ分散化する。
  過度な分散はレイテンシと運用負荷を増やすため、Phase 3 までは単純構成を優先する。
- **データストア**: 時系列（分足・ティック）は列指向／時系列DB、注文・約定・損益は ACID を満たす RDB、
  設定・カタログは Git 管理のファイル。
- **配信**: 内部イベントバス（pub/sub）で疎結合化し、UI へは WebSocket 等でプッシュ配信。
- **接続先**: 証券会社の発注API（自動売買が規約上許容されるもの）を最低1社、可能なら冗長化。
- **稼働環境**: 立会時間中の安定性を優先し、家庭内ネットワーク単独依存を避ける（回線冗長またはクラウド配置）。

| ID | 構成に関する要求 | 優先度 |
|---|---|---|
| NFR-050 | 証券会社・データベンダをアダプタで抽象化し、乗り換え可能とすること | Must |
| NFR-051 | 同一コードでペーパートレード（模擬約定）と実弾を切替えられること | Must |
| NFR-052 | 単一障害点（発注経路、データ経路）を把握し、障害時の縮退動作を定義すること | Should |
